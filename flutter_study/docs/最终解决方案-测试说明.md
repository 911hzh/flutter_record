# Flutter 生命周期清理 - 最终解决方案

## ✅ 最终实施方案：方案 4（混合方案）

### 核心原理

**不强制销毁 FlutterEngine，让系统自动管理资源释放，同时使用 StatefulWidget 的 dispose 进行资源清理。**

## 📝 代码修改总结

### iOS 端修改 (FlutterWidgetVC.swift)

```swift
deinit {
    print("🗑️ FlutterWidgetVC 开始销毁，路由: \(targetRoute)")
    
    // 清理视图层级
    if let flutterVC = self.flutterVC {
        flutterVC.willMove(toParent: nil)
        flutterVC.view.removeFromSuperview()
        flutterVC.removeFromParent()
        self.flutterVC = nil
    }
    
    // 清理 channel（避免内存泄露）
    channel?.setMethodCallHandler(nil)
    channel = nil
    
    // ✅ 关键：不调用 destroyContext()，让 engine 自然释放
    // FlutterEngineGroup 会自动管理资源回收
    self.engine = nil
    
    print("✅ FlutterWidgetVC 销毁完成（engine 将自动释放）")
}
```

**关键改动：**
- ❌ 删除了 `destroyContext()` 调用
- ❌ 删除了延迟销毁的异步代码
- ✅ 简单地设置 `engine = nil`，让 ARC 管理

### Flutter 端修改 (NativeUseFlutterPage.dart)

```dart
class NativeUseFlutterPage extends StatefulWidget {  // ✅ 使用 StatefulWidget
  const NativeUseFlutterPage({super.key});

  @override
  State<NativeUseFlutterPage> createState() => _NativeUseFlutterPageState();
}

class _NativeUseFlutterPageState extends State<NativeUseFlutterPage> {
  StreamSubscription? _eventSubscription;
  
  @override
  void initState() {
    super.initState();
    print("🚀 NativeUseFlutterPage initState");
    _setupEventChannel();
  }
  
  void _setupEventChannel() {
    final eventMessageChannel = EventChannel("FlutterNativeEventChannelBridge");
    _eventSubscription = eventMessageChannel.receiveBroadcastStream().listen(
      (event) => print("📥 EventChannel 收到事件: $event"),
      onError: (error) => print("❌ EventChannel 错误: $error"),
    );
  }

  @override
  void dispose() {
    print("💀 NativeUseFlutterPage dispose 执行");
    
    // ✅ 在 dispose 中清理资源
    _eventSubscription?.cancel();
    _eventSubscription = null;
    
    print("✅ EventChannel 订阅已取消");
    super.dispose();
  }

  @override
  Widget build(BuildContext context) { ... }
}
```

**关键改动：**
- ✅ 从 HookWidget 改为 StatefulWidget
- ✅ 在 initState 中初始化资源
- ✅ 在 dispose 中清理资源（**这个会执行！**）
- ❌ 移除了 useEffect（useEffect 的清理函数在这个场景下不会执行）

## 🎯 为什么这个方案有效？

### 1. iOS 不强制杀死 engine

```
之前：
iOS deinit → destroyContext() → 强制终止 Dart VM → Flutter dispose 不执行 ❌

现在：
iOS deinit → engine = nil → ARC 延迟释放 → Flutter 有机会执行 dispose ✅
```

### 2. 使用 StatefulWidget 的 dispose

```dart
// useEffect 的问题：
useEffect(() {
  return () {
    // 只在 Widget 被 Flutter 路由系统移除时执行
    // 原生关闭不会触发 ❌
  };
}, []);

// dispose 的优势：
@override
void dispose() {
  // 只要 Widget 被标记为需要销毁，就会执行
  // 即使是由原生触发的关闭 ✅
  super.dispose();
}
```

### 3. FlutterEngineGroup 自动管理

- FlutterEngineGroup 会智能管理多个 engine 的生命周期
- 当 engine 没有强引用时，会延迟一段时间再真正销毁
- 这个延迟给了 Flutter 足够的清理时间

## 🎉 解决的问题

### ✅ 问题 1：内存泄露
- **之前：** EventChannel 订阅没有取消，导致内存泄露
- **现在：** dispose 中正确取消订阅

### ✅ 问题 2：dispose 不执行
- **之前：** iOS 强制销毁 engine，dispose 来不及执行
- **现在：** engine 自然释放，dispose 有时间执行

### ✅ 问题 3：useEffect 清理函数不执行
- **之前：** useEffect 依赖 Flutter 路由系统，原生关闭不触发
- **现在：** 使用 dispose，更可靠

### ✅ 问题 4：循环引用
- **之前：** Swift 闭包没有使用 `[weak self]`
- **现在：** 已修复，添加了 `[weak self]`

## ⚠️ 注意事项

### 1. dispose 执行时机

dispose 会在以下情况执行：
- ✅ Flutter 路由 pop
- ✅ 原生 ViewController dismiss（使用此方案后）
- ✅ Widget 从树中移除

### 2. 与 useEffect 的区别

```dart
// useEffect 清理函数：只在 Flutter 路由变化时执行
useEffect(() => () { cleanup(); }, []);

// dispose：只要 Widget 销毁就执行（更可靠）
@override
void dispose() { cleanup(); super.dispose(); }
```

### 3. 何时使用 useEffect vs dispose

| 场景 | 推荐 |
|-----|------|
| 原生嵌入 Flutter | **dispose** ✅ |
| 纯 Flutter 应用 | useEffect 或 dispose 都可以 |
| 需要响应依赖变化 | **useEffect** ✅ |
| 简单的资源清理 | **dispose** ✅ |

## 🎊 总结

通过这次修复，我们学到了：

1. **原生和 Flutter 的生命周期不同步**
   - 原生销毁不等于 Flutter 销毁
   - 需要给 Flutter 时间清理

2. **不要强制销毁资源**
   - 让系统自动管理更可靠
   - ARC 和 GC 知道什么时候该释放

3. **dispose 比 useEffect 清理函数更可靠**
   - 在原生嵌入 Flutter 的场景下
   - dispose 的触发条件更宽松

4. **使用强引用保持对象生命周期**
   - 在异步闭包中捕获强引用
   - 避免过早释放

现在你的项目应该不会有内存泄露了！🎉
